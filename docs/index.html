DOCUMENTATION

COAR Notify

What is this?

Inbox Viewer is a web interface to browse, inspect, validate and send notifications using the COAR Notify protocol. It reads the notifications in an LDN inbox, checks them with a JSON Schema and SHACL validator, and lets you reply to them or create new ones.

The interface is deliberately technical and stays close to the raw information that is sent and received using the COAR Notify protocol. It is aimed at technical managers of repositories and service providers who want to debug their COAR Notify service endpoints.

Configuration

To get the most out of the Inbox Viewer, open the Settings screen (the ⚙️ button in the main application). Settings are stored in your browser and apply only to that browser.

The main configuration settings for first-time users are listed below.

  • Main inbox – the LDN inbox whose notifications are shown in the inbox list (default: ).
  • Validator endpoint – the validator used by the Validate button (default: ).
  • Relay endpoint and Relay token – by default, notifications are sent directly from your browser. Some repository systems, however, only accept notifications from a fixed IP address. For those, the Inbox Viewer offers a relay endpoint that forwards outgoing notifications from a fixed address. Using the relay requires a relay token, which can be requested from the service manager at EMAIL.
  • Your Actor Identity – fill in the id, type, name and (optional) inbox of the actor that sends the notifications.

Inbox

The Inbox page provides an overview of all incoming notifications. This page is not live. Refresh the page to see new notifications. The inbox always contains some example notifications. Incoming notifications are removed automatically after days.

The following fields are shown for each notification:

  • Type – the activity type of the notification, e.g. Offer, Announce or Accept.
  • Name – the file name of the notification in the inbox. Click it to open the notification.
  • Actor – the identifier of the actor that sent the notification.
  • Size – the size of the notification in bytes.
  • Modified – the date and time when the notification was stored in the inbox.

Notification

The notification page shows a single notification. The badge next to the title shows whether a reply is expected. Only Offer notifications expect a reply. Click the URL below the title to open the raw notification.

Three views are available:

  • Details – a summary and the parsed body of the notification.
  • Source – the raw JSON-LD.
  • Graph – the notification as an RDF graph.

The buttons below the notification are grouped by purpose:

  • Check – Validate sends the notification to the validator and shows the report.
  • Decide – Accept or Reject the offer.
  • Report – Flag the offer.
  • Inform – Announce a result related to the offer.

A reply button opens a form to compose the reply before it is sent.

Validate

Validate sends the raw notification to the validator set as Validator endpoint on the Settings screen. The validator runs two checks:

  • JSON Schema – checks that the JSON conforms to the COAR Notify guidelines. This catches interoperability issues. See the JSON Schema.
  • SHACL – checks the semantic (RDF) content of the notification. See the SHACL shapes.

The report is shown below the buttons as Validation Report.

If the validator cannot be reached or returns an error, the report shows Failed to contact followed by the validator URL. Check the Validator endpoint setting and that the validator is running.

Reply

Each reply button opens a form. The To fields are filled in from the offer: the reply goes to the inbox of the offer's origin, or of its actor when the origin has none. A Default reply inbox on the Settings screen overrides this. The reply uses Your Actor Identity and Your Origin Identity from the Settings screen, contains the offer as its object and refers to it with inReplyTo.

Send delivers the reply, directly from the browser or through the relay when a Relay endpoint is set. With the relay, a trace of the delivery is shown. Reset restores the form.

Accept

Accept the offer. Check Tentative Accept to send a TentativeAccept instead. A tentative accept requires a Summary.

Reject

Reject the offer. Check Tentative Reject to send a TentativeReject instead. A tentative reject requires a Summary.

Flag

Flag the offer, e.g. when it cannot be processed. A Summary explaining why is required.

Announce

Announce the result of the offer. Pick the Announce Type: GenericAction, EndorsementAction, RelationshipAction or ReviewAction. It is preselected when the offer is a review or endorsement request.

  • What – the result, e.g. the review or endorsement: its Object URL, Cite As and Type. For a RelationshipAction: the Subject, Relationship and Object of the relationship.
  • Context – the work the result is about. Filled in from the offer.

New Notification

The New Notification page (New Notification button in the upper-right menu) creates a notification from scratch. The buttons are grouped by purpose: Request (Offer), Inform (Announce), Retract (Undo) and Custom (Generic).

Each form starts with the To fields: the Inbox to send to and, optionally, the id, name and type of the target. Sending works as for a reply.

Offer

Request a service, e.g. a review or an endorsement. Pick the Offer Type: EndorsementAction or ReviewAction. Then describe the work:

  • Id (landing page) – the landing page URL of the work. Required.
  • Cite As – a citable URL of the work, e.g. a DOI.
  • Type – the ActivityStreams and schema.org type of the landing page.
  • Item (content resource), Media Type and Type – the content itself, e.g. the PDF. Required.

Announce

Announce a result without a preceding offer. The form is the same as the Announce reply, but Context starts empty and is optional.

Undo

Retract a previous offer. Pick the offer from the list; the To fields are filled in from its target. A Summary explaining why is required. The offer is sent as the object of the Undo.

In this demo the list shows the offers in the main inbox. A production system would list the offers it sent itself.

Generic

Send any JSON document to an inbox. Optionally pick an existing notification as a template, then edit the source. Only JSON is accepted. For debugging only: nothing is added or checked before sending.

Advanced Configuration

Configure your own LDN Inbox

The Inbox Viewer can read any remote inbox that follows the LDN protocol. Set its URL as Main inbox on the Settings screen, with a trailing slash.

The inbox must provide:

  • GET on the inbox URL – an LDP container listing the notifications with ldp:contains. Served as application/ld+json or text/turtle.
  • GET on each notification URL – the notification as JSON-LD. Notification URLs must be under the inbox URL.
  • POST on the inbox URL – accepts a new notification as application/ld+json. Only needed to send to this inbox.
  • CORS – the browser reads the inbox directly, so the server must allow the origin of the Inbox Viewer, including the Accept and Content-Type headers.

Optionally, add posix:mtime (seconds since 1970) and posix:size (bytes) per notification to fill the Modified and Size columns. A minimal container: 

{
  "@context": {
    "ldp": "http://www.w3.org/ns/ldp#",
    "posix": "http://www.w3.org/ns/posix/stat#"
  },
  "@id": "https://example.org/inbox/",
  "@type": "ldp:Container",
  "ldp:contains": [
    {
      "@id": "https://example.org/inbox/1234.jsonld",
      "posix:mtime": 1759046400,
      "posix:size": 1024
    }
  ]
}
